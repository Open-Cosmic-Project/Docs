# CosmicOS — Cambios y Decisiones Pendientes (v0.2.8)

*Fecha de registro: 6 de noviembre de 2026*

Este documento consolida las decisiones acordadas por el autor y las propuestas técnicas en curso para ser incorporadas en la próxima versión formal de la especificación (**v0.2.8**).

---

## 1. Organización y Repositorios (Sección 8.7)

| Estado | Aspecto | Detalle de la Decisión |
|---|---|---|
| **[Acordado]** | Multi-repo | Cada carpeta del árbol es un repositorio Git independiente, gestionado centralizadamente con `repo` y un manifiesto XML. |
| **[Acordado]** | Organización | `OpenCosmicProject` (OCP) es el nombre y la organización oficial en GitHub/GitLab. |
| **[Acordado]** | Documentación | La carpeta `Docs/` se mantiene con mayúscula inicial para indicar que es documentación de arquitectura general del proyecto y no un módulo del código fuente del sistema operativo. |
| **[Propuesto]** | Manifiesto | `cosmic-manifest` es un repositorio propio dentro de OCP que contiene el archivo `default.xml` y define los bloqueos de versión de todo el ecosistema. |

---

## 2. Construcción y Cargo Workspace

| Estado | Aspecto | Detalle de la Decisión |
|---|---|---|
| **[Acordado]** | `default-members` | El archivo `Cargo.toml` raíz delimita la compilación por defecto al **Hito 1** de la hoja de ruta: `core/cinitd`, `core/kernel.root`, `core/clauncher`, `pkg/sps`, `libs/cosmic-core` y `tools/cosmic-repo`. |
| **[Acordado]** | Exclusiones en Git | Archivo `.gitignore` configurado para ignorar `target/`, artefactos de compilación y el sub-árbol `kernel/linux/` (que es gestionado como repo propio). |
| **[Propuesto]** | Repo de Construcción | Creación de un repositorio auxiliar `cosmic-build` que contenga el `Cargo.toml`, `Cargo.lock` y scripts de empaquetado, enlazados en la raíz mediante `<linkfile>` en el manifiesto. |

---

## 3. Kernel Endurecido y Podado

| Estado | Aspecto | Detalle de la Decisión |
|---|---|---|
| **[Acordado]** | Purga de `arch/` | Kernel Linux modificado en el que se eliminan todas las arquitecturas excepto `arm64` y `riscv`. |
| **[Acordado]** | Parámetros fijos | Parámetros de arranque del kernel fijados en tiempo de compilación. |
| **[Propuesto]** | Fork oficial | Repositorio `linux` bajo OCP, sincronizado con `clone-depth="1"`. Ramas de versión upstream `cosmic/6.x` con commits limpios de purga. |
| **[Propuesto]** | Script reproducible | Script [`../kernel/scripts/purge-arch.sh`](../kernel/scripts/purge-arch.sh) para regenerar y auditar la purga de `arch/` de manera determinista contra cualquier tag LTS upstream. |
| **[Propuesto]** | Poda de drivers | Los drivers no se borran del árbol; la poda se realiza vía Kconfig (`make savedefconfig`). El TCB se audita por los objetos `.o` compilados. |
| **[Abierto]** | Variantes de cmdline | Determinar si se ofrece una variante de kernel con línea de comandos libre en los canales Quasar/EventHorizon o si permanece estricta en todos los canales. |

---

## 4. CinitD y Librería Estándar C (libc)

| Estado | Aspecto | Detalle de la Decisión |
|---|---|---|
| **[Acordado]** | libc del sistema | `glibc` se mantiene como la librería estándar para el sistema base y las aplicaciones de usuario. |
| **[Propuesto]** | libc de CinitD | Enlace estático con `musl` para `cinit-early` y `cinitd` (PID 1) para garantizar un binario completamente autónomo y sin dependencias dinámicas. Transitoriamente se inicia con glibc. |

---

## 5. Decisiones Pendientes por Cerrar

1. **Parámetros fijos del kernel:** ¿Deben vivir exclusivamente en los archivos `defconfig` (`CONFIG_CMDLINE`) o aplicarse mediante un parche en el código fuente de inicio del kernel?
2. **Poda adicional de drivers:** ¿Se mantendrá estrictamente a nivel Kconfig o se aplicarán podas puntuales de carpetas hoja mediante scripts?
3. **Roles en D-40:** Detallar formalmente el alcance exacto de `cosmic-core` (librería compartida), `cosmic-flash` (herramienta de flasheo) y `cosmic-repo` (gestor de índices TUF).
4. **Prototipado de CinitD (D-25):** Confirmar si el desarrollo inicia directamente sobre CinitD en Rust en QEMU o si se emplea un init temporal durante la validación del sandbox de `clauncher`.
